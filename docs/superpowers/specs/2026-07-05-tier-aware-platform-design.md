## 1. Why this exists (context)

**Learning Hungarian** is being promoted from a concept site (hand-coded static
HTML lessons on GitHub Pages) into a real product: a free, interactive resource
that takes an English speaker from zero to **B2 across all four skills**
(reading, writing, listening, speaking).

The existing repo already contains ~30 machine-authored HTML lessons (Lessons
1–33, A1 through mid-B1). These were generated by a prior automated run down the
roadmap. They are **reference material only** — the Hungarian is unreviewed and
they use a copy-paste inline-JS-per-file pattern that does not scale to 52
lessons plus shared systems (SRS, progress, audio, AI). We re-author, we do not
port.

This spec covers **Sub-project 1 of 5** — the foundation everything else builds
on. It deliberately excludes AI and audio *features* but builds the data model
and adapters they will plug into.

### Locked product decisions (from brainstorm 2026-07-05)

| Decision | Choice |
|---|---|
| Architecture | Dockerized app + backend (not static). HAL for testing → A2 VPS later. |
| B2 scope | Full four skills (reading, writing, listening, speaking). |
| Framework | **SvelteKit** (TypeScript), SSR + API routes in one deployable. |
| Database | **PostgreSQL**. |
| Auth / accounts | **Accounts from day one** — self-hosted session auth (Oslo/Arctic), email + OAuth. |
| AI cost model | **Hybrid** — metered free quota on the platform key + unlimited with a user-supplied key. |
| AI provider | Provider-agnostic adapter, **Claude default**. |
| Listening (TTS) | Pre-generate fixed lesson audio once → static files; live TTS only for dynamic AI output. |
| Speaking (STT) | Self-hosted **Whisper** on HAL + Claude for feedback. |
| Content model | **Tier-aware engine** — all CEFR levels (A1–C2) structurally supported from day one. |
| Content authoring order | Bottom-up **A1 → A2 → B1 → B2** (C1/C2 = "beyond", later). |
| Content accuracy | **Two-layer validation, no paid tutor**: (1) authoring-time **Mixture of Experts** — cross-validate flagged Hungarian with a second model (Codex) vs Claude; (2) runtime **crowd-sourced feedback loop** → GitHub issues → agent triage + Codex validation → implement/reject → thank-you email. |
| Product domain | **nyolc.cc** (Hungarian *nyolc* = "eight"); transactional mail from `noreply@nyolc.cc`. |

### The 5 sub-projects (product-level roadmap)

1. **Platform + Lesson Engine (this spec)** — Dockerized SvelteKit+Postgres+auth on HAL; tier-aware content model; core (text-based) exercise types; progress tracking; SRS scaffold; A1 content re-authored as first seed. **Includes the "Provide feedback / corrections" button + GitHub-issue creation** (data collection starts as soon as lessons exist; the agent that processes those issues is SP6).
2. **AI Tutor Layer** — conversation partner (speaking) + writing grading; provider-agnostic adapter; hybrid metering enforcement.
3. **Audio Layer** — TTS pre-generation pipeline; listening-comprehension exercises; Whisper speaking assessment.
4. **Content Production** — remaining lessons via a repeatable authoring pipeline built on the **Mixture-of-Experts** validation strategy (§7.5).
5. **B2 Assessment** — four-skill mock exams + a readiness dashboard.
6. **Feedback & Continuous Validation Loop** — the agent pipeline that consumes crowd-sourced feedback issues: triage → evaluate → Codex-validate → implement/reject → thank-you email from `noreply@nyolc.cc` (§7.5).

Each sub-project gets its own spec → plan → build cycle.

## 2. Scope of Sub-project 1

### In scope

- SvelteKit + Postgres app, containerized with Docker Compose, deployable to HAL.
- User accounts: email/password + at least one OAuth provider; sessions; email verification path.
- **Tier-aware content data model** (`tier → module → lesson → exercise`) supporting all CEFR levels.
- Content authored as **structured data** (not hand-coded HTML), rendered by shared Svelte components.
- **Core exercise types** (text/interaction only — no audio, no AI): fill-in-blank, multiple choice, dropdown selection, card flip, sentence building (word tiles), transformation, dialogue completion.
- **Accent-aware answer validation** (distinguishes wrong vs. missing-diacritic vs. correct).
- **Progress tracking** — per-user lesson completion, per-exercise scores, resume position (server-side, since accounts exist from day one).
- **SRS scaffold** — data model + scheduling algorithm for review items, seeded by lesson vocabulary/grammar items. UI can be minimal in this sub-project; the engine and data must be correct.
- **AI usage-metering data model** — tables/columns to record per-user AI consumption and BYO-key presence, so Sub-project 2 can enforce the hybrid model without a migration. No AI calls yet.
- **Re-authored A1 seed content** — the three foundation lessons (alphabet, vowel sounds, verb "to be") plus enough additional A1 lessons to prove the engine end-to-end (target: Foundation module + a few A1 lessons).
- Curriculum index / navigation driven by the content model.
- **Feedback capture** — a "Provide feedback / corrections" control on each lesson/exercise that files a structured GitHub issue with lesson + exercise context and the submitter's optional email (for the outcome notification). The *processing agent* is SP6; SP1 only captures.
- Deploy runbook for HAL.

### Out of scope (deferred to later sub-projects)

- Any AI feature (conversation, grading) — Sub-project 2.
- Any audio (TTS playback, listening exercises, Whisper STT) — Sub-project 3.
- Full A2/B1/B2 content authoring — Sub-project 4.
- Mock B2 exams and readiness dashboard — Sub-project 5.
- Public launch, custom domain, A2 VPS migration — post-MVP.

### Explicit non-goals

- We do **not** port the existing 30 HTML lessons. They inform coverage and exercise design; content is re-authored fresh in the structured format.
- We do **not** keep GitHub Pages as the production host. The static site may remain live until the new app supersedes it.

## 3. Architecture

### 3.1 Runtime topology (Docker Compose)

```
┌──────────────────────────────────────────────┐
│ HAL (Docker host)                             │
│                                               │
│  ┌────────────┐   ┌────────────┐              │
│  │ app        │   │ postgres   │              │
│  │ SvelteKit  │──▶│ (data)     │              │
│  │ (Node)     │   └────────────┘              │
│  └─────┬──────┘                               │
│        │  (adapter seam, no calls yet)        │
│        ▼                                       │
│   [ AI adapter ]   [ audio/Whisper ]  ← SP2/3 │
│   (interfaces defined, impls deferred)        │
└──────────────────────────────────────────────┘
```

- Single `app` container (SvelteKit built with `adapter-node`), a `postgres`
  container, and a named volume for DB data.
- AI and Whisper services are **interface seams** now — defined as adapter
  contracts, implemented in later sub-projects. Compose file leaves room for
  them but does not run them yet.
- Portable: the same Compose stack runs on HAL and any A2 VPS. Shared cPanel
  hosting is explicitly ruled out (cannot run persistent containers).

### 3.2 Layering inside the app

- **Content layer** — structured lesson data (see §4), version-controlled in the
  repo, loaded into Postgres via a seed/import step (content is authored in the
  repo as the source of truth; DB is the runtime store).
- **Engine layer** — exercise rendering + validation components, progress
  service, SRS service.
- **Account layer** — auth, sessions, user profile, AI-metering ledger.
- **Adapter layer** — `AIProvider` and `SpeechProvider` interfaces (stubs now).

### 3.3 Key library choices

- Auth: **Oslo + Arctic** (post-Lucia session primitives) — self-hosted, no
  per-MAU vendor fee, runs anywhere.
- DB access: a typed query layer (Drizzle ORM recommended for TS-native
  migrations; final call at plan time).
- Styling: keep **Tailwind** (already the project's idiom) — via the build
  pipeline now, not the CDN.
- Testing: Vitest (unit) + Playwright (end-to-end for exercise flows).

## 4. The tier-aware content model (the core scaffold)

This is the heart of Sub-project 1 — get it right and every future tier/skill
slots in without rework.

### 4.1 Hierarchy

```
CEFRTier (A1, A2, B1, B2, C1, C2)   — all six exist from day one, may be empty
  └── Module            (a themed group, e.g. "Foundation", "Cases I")
        └── Lesson      (one teachable unit)
              ├── Content blocks   (explanation, tables, examples)
              └── Exercise[]       (typed interactive items)
```

### 4.2 Data-model sketch (finalize at plan time)

- `cefr_tier` — enum/reference; ordered; `is_published` flag per tier.
- `module` — belongs to a tier; ordered; title, description.
- `lesson` — belongs to a module; ordered; slug, title, objectives, prerequisites (lesson refs), estimated minutes, `skill_tags` (reading/writing/listening/speaking — for future filtering), status (`draft`/`reviewed`/`published`).
- `content_block` — belongs to a lesson; ordered; typed (prose, table, example, callout).
- `exercise` — belongs to a lesson; ordered; `type` (see §5); typed `payload` (JSON) holding prompt/answer/options/translation; `srs_items` linkage.
- `srs_item` — an atomic reviewable (a vocab pair or grammar pattern); may be referenced by many exercises.

### 4.3 Content as source of truth

Lessons are authored as structured files **in the repo** (YAML/JSON/Markdown-with-frontmatter — final format chosen at plan time), reviewed via PR, and imported into Postgres by a seed command. This keeps content diffable, reviewable, and the "expert review gate" enforceable in Git — while the runtime reads from the DB.

### 4.4 Progression / gating

- A learner has a position per tier; lessons unlock by prerequisite satisfaction.
- Tiers are authored bottom-up; an unpublished tier is simply hidden.
- "Zero-to-hero" holds because A1 is authored first and a beginner can start at lesson one.

## 5. Lesson engine & exercise types

Each exercise type is one Svelte component with a shared contract:
`render(payload) → user input → validate() → {correct | partial | wrong} + feedback`.

Core types for this sub-project (text/interaction only):

| Type | Interaction | Validation notes |
|---|---|---|
| Fill-in-blank | Text input, Enter to check | Accent-aware compare |
| Multiple choice | Button/radio select | Exact match |
| Dropdown selection | `<select>` | Exact match |
| Card flip | Click to reveal | Self-graded → feeds SRS |
| Sentence building | Sortable word tiles | Order compare |
| Transformation | Free text | Accent-aware compare + model answer |
| Dialogue completion | Sequential inputs | Per-gap accent-aware compare |

**Accent-aware validation** is a first-class engine feature: normalize input,
compare against answer, and classify the result as *correct*, *right word but
missing/incorrect diacritics* (á/é/í/ó/ö/ő/ú/ü/ű), or *wrong*. Feedback differs
per class — this directly serves Hungarian's diacritic-heavy orthography.

Listening and speaking exercise types are defined in the type enum now but
implemented in Sub-project 3.

## 6. Accounts, progress, SRS, and AI-metering

### 6.1 Accounts (from day one)

- Email/password (hashed with a modern KDF) + email verification.
- At least one OAuth provider (Google recommended — fits the audience).
- Server-side sessions (Oslo), secure cookies.
- Minimal profile: display name, locale, learning-goal tier target (default B2).

### 6.2 Progress (server-side)

- Per-user, per-lesson: status, first-attempt accuracy, best score, last visited.
- Resume position across devices (the reason accounts exist from day one).

### 6.3 SRS scaffold

- Algorithm: a proven, simple scheduler (SM-2-style or FSRS-lite — chosen at plan time) operating over `srs_item`s.
- Each answered exercise updates the linked SRS items' intervals.
- This sub-project must produce **correct scheduling data**; a full review-session UI can be minimal and expanded later.

### 6.4 AI-metering ledger (data only, no calls)

- `ai_usage` ledger: per-user counters/timestamps for future quota enforcement.
- `user.byo_key` presence flag + encrypted-at-rest storage design (implemented in SP2, schema reserved now).
- Purpose: Sub-project 2 enforces the hybrid model without a schema migration.

## 7. Handling the existing corpus (reference-only)

- The ~30 HTML lessons stay in `lessons/` untouched as reference.
- For each lesson we author fresh in the structured format, we may mine the old
  file for **exercise ideas, vocabulary lists, and coverage** — never for
  trusted Hungarian. Every re-authored lesson passes an accuracy review before
  `status: reviewed`.
- Once the engine renders equivalent content, the old static site is retired
  (kept in history, not deleted destructively).

## 7.5 Content validation & feedback loop

This is how the product reaches B2-grade accuracy **without a paid tutor** — the
answer to the long-pole risk. Two layers.

### Layer 1 — Authoring-time Mixture of Experts (MoE)

- Content is authored by one model, then any lesson/section **flagged as
  `needs-assessment`** is cross-validated by a **second, independent model
  (Codex/GPT)** checking the Hungarian against Claude's version.
- **Agreement → `status: reviewed`.** **Disagreement → held** with both models'
  notes attached for a human (Jaypaul) tie-break, or a third opinion.
- Runs in this very environment (`codex` is available as a cross-checker), and
  becomes the backbone of the Content Production pipeline (SP4).
- The MoE verdict and model identities are recorded on the lesson for provenance
  ("validated by Claude + Codex, 2026-07-05").

### Layer 2 — Runtime crowd-sourced validation matrix

Real learners are the distributed review board. Flow:

```
[Lesson/exercise] --"Provide feedback / corrections"-->
  GitHub issue (auto-filled: tier, lesson slug, exercise id,
                current content, user's correction, optional email)
    --> Agent pipeline (SP6):
          1. Triage      — dedupe, classify (typo / grammar / factual / pedagogy)
          2. Evaluate    — assess the claim against sources
          3. Validate    — Codex cross-check (same MoE gate as Layer 1)
          4. Decide      — implement (PR to content) or reject (with reason)
          5. Notify      — email from noreply@nyolc.cc thanking the submitter
                           and stating the outcome (accepted+shipped / declined+why)
```

- **Same MoE gate** guards crowd corrections — no unreviewed change reaches
  content; a submitted "fix" is itself cross-validated before merge.
- **Loop closure is the retention hook**: every contributor hears back, by name,
  with a real outcome. Costs nothing, compounds goodwill, and turns corrections
  into a growing accuracy flywheel.
- **SP1 builds only the capture end** (button → issue). The processing agent,
  email sending, and PR automation are **SP6**.

### Infra this introduces (decided at plan time)

- A **GitHub issue template** + labels (`feedback`, `needs-assessment`,
  `content`, tier labels).
- **Transactional email** for `noreply@nyolc.cc` (service vs self-hosted SMTP —
  see open questions). The thank-you/outcome **templates get Jaypaul's approval
  once**, then send automatically (they are templated transactional notices, not
  bespoke human correspondence).
- The **SP6 agent** may run as a GitHub Action or a HAL cron job.

## 10. Risks & open questions

- **HAL capabilities** — confirm Docker + reverse-proxy/TLS pattern on HAL before build. (Assumed available; verify.)
- **Content accuracy** — *resolved in principle* (§7.5): authoring-time MoE (Claude + Codex) plus a runtime crowd-sourced feedback loop replace a paid tutor. Residual risk: MoE can share blind spots (two LLMs agreeing on the same wrong Hungarian). Mitigations: cite authoritative sources in-prompt, weight crowd corrections heavily, and keep Jaypaul as tie-breaker on held disagreements.
- **Transactional email deliverability** — `noreply@nyolc.cc` needs SPF/DKIM/DMARC set up or thank-you notes land in spam. Resolve when choosing the email path.
- **ORM/content-format finalization** — Drizzle vs alternatives; YAML vs JSON vs MD-frontmatter for authored content. Decide at plan time.
- **SRS algorithm choice** — SM-2 vs FSRS-lite. Decide at plan time.
- **"Free forever" vs AI cost** — resolved in principle (hybrid), enforced in SP2. Keep the free core genuinely free.
- **Scope discipline** — accounts-from-day-one plus a tier-aware engine is already a substantial MVP; resist pulling AI/audio forward.
