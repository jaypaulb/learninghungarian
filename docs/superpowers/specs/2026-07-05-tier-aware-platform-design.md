## 1. Why this exists (context)

**Learning Hungarian** is being promoted from a concept site (hand-coded static
HTML lessons on GitHub Pages) into a real product: a free, interactive resource
that takes an English speaker from zero to **B2 across all four skills**
(reading, writing, listening, speaking), with the concrete goal of **passing an
accredited Hungarian B2 exam for residency**.

The existing repo already contains ~30 machine-authored HTML lessons (Lessons
1–33, A1 through mid-B1), generated by a prior automated run. They are
**reference material only** — the Hungarian is unreviewed and they use a
copy-paste inline-JS pattern that does not scale to 52 lessons plus shared
systems (SRS, progress, audio, AI). We re-author; we do not port.

This spec covers **Sub-project 1 of 6** — the foundation everything else builds
on. It excludes AI and audio *features* but builds the data model and adapter
seams they plug into.

### Locked product decisions

### The 6 sub-projects

1. **Platform + Lesson Engine (this spec)** — Dockerized SvelteKit+Postgres+OAuth on HAL; tier-aware content model; core text exercise types; progress; SRS scaffold; A1 seed content re-authored; **feedback capture** (private-first, no PII in GitHub).
2. **AI Tutor Layer** — conversation (speaking) + writing grading; provider-agnostic adapter; hybrid metering + BYO-key key-management.
3. **Audio Layer** — TTS pre-generation; listening exercises; Whisper speaking assessment.
4. **Content Production** — remaining lessons via the MoE authoring pipeline (§7.5), with source-citation requirements.
5. **Tiered Assessment** — milestone exams at A1/A2/B1/B2, B2 mirroring the accredited residency exam; readiness dashboard.
6. **Feedback & Continuous Validation Loop** — trust-tiered agent pipeline consuming feedback: triage → Codex-validate → auto-merge (trusted) or human-gate (new) → thank-you email from `noreply@nyolc.cc`.

## 2. Scope of Sub-project 1

### In scope

- SvelteKit + Postgres app, Dockerized (Compose), deployable to HAL.
- **OAuth-only accounts (Google)** + server-side sessions (Oslo/Arctic). CSRF protection, session rate-limiting. **GDPR account delete + data export.**
- **Tier-aware content model** (§4) — `tier → module → lesson → {content, exercise, assessment}` with **stable content IDs + content versioning**.
- Content authored as **structured data in-repo** (source of truth), imported to Postgres via an **idempotent** import command with defined progress-migration behavior.
- **Core exercise types** (text/interaction only): fill-in-blank, multiple choice, dropdown, card flip, sentence building, transformation, dialogue completion — each with a **versioned, type-discriminated JSONB payload**.
- **Accent-aware validation** (wrong vs. missing-diacritic vs. correct).
- **Per-tier assessment** rendering (using existing exercise types for SP1; skill-specific/audio items arrive in SP3/SP5). A1 assessment authored as the first example.
- **Progress tracking** — server-side, per-user, resumes across devices.
- **SRS scaffold** — `user_srs_state` keyed by **item × skill × modality × direction**, with attempt history and review-eligibility. Scheduler correct; review UI minimal.
- **Feedback capture** — a "Provide feedback / corrections" control that writes **privately to Postgres first** (lesson/exercise ref, correction text, optional email held privately, explicit consent). A sanitized GitHub issue (internal ID, **no email/PII**) is created for the SP6 pipeline. Rate-limited; basic input sanitization against injection.
- **Honest content-status badge** on every lesson (`provisional` / `community-verified`) with source citations surfaced.
- Curriculum index / navigation driven by the content model (A1–B2 only).
- Deploy runbook + migration command + health check + backup/restore drill for HAL.

### Out of scope (later sub-projects)

- Any AI feature (SP2). Any audio (SP3). Full A2–B2 content (SP4). Full tiered exams + residency-exam mirroring (SP5). Feedback processing agent, email sending, trust/reputation system, auto-merge (SP6).
- Email+password auth; additional OAuth providers. Public launch, custom domain, A2 VPS migration, CI image-publishing pipeline.

### Explicit non-goals

- We do **not** port the existing 30 HTML lessons (reference only).
- SP1 **validates the text engine and a four-skill-*ready* data model** — it does **not** claim to validate the four-skill *experience* (audio/AI come later). Schema-level acceptance tests confirm listening/speaking/assessment items fit the model.

## 3. Architecture

### 3.1 Runtime topology (Docker Compose)

```
HAL (Docker host)
  app (SvelteKit / adapter-node)  ──▶  postgres (named volume)
        │  adapter seams (interfaces only in SP1)
        ▼
   [ AIProvider ]  [ SpeechProvider ]   ← implemented SP2 / SP3
```

- One `app` container, one `postgres` container, named volume for data.
- AI/Whisper are **interface seams** now; Compose reserves room, runs neither yet.
- Same Compose stack on HAL and any A2 **VPS** (shared cPanel is ruled out).

### 3.2 Layers

- **Content** — structured lesson/assessment data in-repo → imported to Postgres.
- **Engine** — exercise + assessment rendering/validation, progress service, SRS service.
- **Account** — OAuth, sessions, profile, GDPR export/delete, AI-metering ledger.
- **Adapter** — `AIProvider` / `SpeechProvider` interfaces (stubs now).

### 3.3 Libraries

- Auth: **Oslo + Arctic** (self-hosted sessions + OAuth), Google provider.
- DB: **Drizzle** ORM; migrations generated and are the deploy path (no ad-hoc schema in seed logic).
- Styling: **Tailwind** via the build pipeline (not CDN).
- Tests: **Vitest** (unit) + **Playwright** (e2e exercise + auth flows).

## 4. Tier-aware content model (the core scaffold)

Get this right and every future tier/skill slots in without rework.

### 4.1 Hierarchy

```
CEFRTier (A1, A2, B1, B2; C1/C2 enum-extensible, not seeded)
  └── Module
        └── Lesson
              ├── ContentBlock[]   (prose, table, example, callout)
              ├── Exercise[]       (typed, versioned JSONB payload)
              └── (tier) Assessment  (milestone per tier)
```

### 4.2 Model sketch (Drizzle; finalize field-level at plan time)

- `cefr_tier` — ordered; `is_published`.
- `module` — belongs to tier; ordered.
- `lesson` — belongs to module; **stable public ID + `content_version`**; slug, objectives, prerequisites, `skill_tags`, `status` (`draft`/`reviewed`/`community-verified`), provenance (authoring + MoE models, source citations).
- `content_block` — typed, ordered.
- `exercise` — **stable ID + `content_version`**; `type`; **`payload_schema_version` + discriminated JSONB `payload`**; links to `srs_item`s; objective/CEFR mapping.
- `assessment` — belongs to a tier; composed of exercise/task refs; blueprint mapping to CEFR/exam competencies (B2 → accredited exam format).
- `srs_item` — atomic reviewable (vocab pair / grammar pattern), stable ID.
- `user_srs_state` — **per user × item × skill × modality × direction**; interval, ease, due-at, attempt history, eligibility.
- `progress` — per user × lesson/exercise (by stable ID + version): status, first-attempt accuracy, best score, last-visited.
- `feedback` — private: user (nullable), lesson/exercise ref + version, correction text, optional email, consent flag, status; the GitHub issue stores only the `feedback.id`.
- `ai_usage` — per-user metering ledger (no calls in SP1).

### 4.3 Content = source of truth, versioned

Lessons/assessments authored in-repo (format — YAML/JSON/MD-frontmatter — fixed at plan time), reviewed via PR, imported by an **idempotent** command keyed on stable IDs. Editing content bumps `content_version`; progress/SRS rows reference `(id, version)` so a changed exercise doesn't silently corrupt history — the import defines whether progress carries forward or resets per change type.

### 4.4 Progression / gating

- Lessons unlock by prerequisite satisfaction; a tier's **milestone assessment** gates advancement to the next tier.
- Tiers authored bottom-up; unpublished tiers hidden. A1-first keeps "zero-to-hero" true.

## 5. Lesson engine & exercise types

Each type is one Svelte component with a shared contract:
`render(payload) → input → validate() → {correct | partial | wrong} + feedback`.

| Type | Interaction | Validation |
|---|---|---|
| Fill-in-blank | Text input | Accent-aware |
| Multiple choice | Select | Exact |
| Dropdown | `<select>` | Exact |
| Card flip | Reveal | Self-graded → SRS |
| Sentence building | Word tiles | Order compare |
| Transformation | Free text | Accent-aware + model answer |
| Dialogue completion | Sequential inputs | Per-gap accent-aware |

- **Accent-aware validation** is first-class: classify input as *correct*, *right word / wrong-or-missing diacritics* (á é í ó ö ő ú ü ű), or *wrong*, with distinct feedback.
- **Payloads are versioned + type-discriminated JSONB**, so adding listening/speaking/assessment item types later is additive (no schema migration).
- **Coverage rule:** every lesson objective maps to ≥1 exercise, and exercise types map to CEFR outcomes — the engine proves *progression*, not just rendering.
- Listening/speaking types are declared in the enum now, implemented in SP3.

## 6. Accounts, progress, SRS, metering

### 6.1 Accounts (OAuth-only, day one)

- **Google OAuth** + server-side sessions (Oslo); secure cookies; **CSRF**; session/login **rate-limiting**.
- Minimal profile: display name, locale, goal tier (default B2-for-residency).
- **GDPR:** self-serve **data export + account deletion** (required even with OAuth).
- No password storage/reset/verification in SP1 (deferred with email+password).

### 6.2 Progress (server-side)

- Per user, per lesson/exercise (by stable ID + version): status, first-attempt accuracy, best score, resume position — cross-device.

### 6.3 SRS scaffold

- `user_srs_state` per **item × skill × modality × direction** with attempt history.
- Scheduler: SM-2 or FSRS-lite (final call at plan time); each answer updates linked items. SP1 produces correct scheduling data; review-session UI minimal.

### 6.4 AI-metering ledger (data only)

- `ai_usage` counters for future quota enforcement.
- **No reserved BYO-key column** — key management (envelope encryption, rotation, redaction, deletion, never-echo-to-UI) is designed and added in **SP2**; SP1 leaves only a clean migration path.

## 7. Existing corpus (reference-only)

- The ~30 HTML lessons stay untouched as reference; we mine them for exercise ideas, vocab, and coverage — **never trusted Hungarian**.

## 7.5 Content validation & feedback loop

The path to B2-grade accuracy **without a paid tutor**. Two layers.

### Layer 1 — Authoring-time (Sources + MoE)

- Author with one model; **every publishable Hungarian item must cite an authoritative source** (grammar reference, corpus, dictionary).
- A **second model (Codex) cross-validates** flagged content vs. the source + first author. Agreement + citation → `status: reviewed`, **shown to learners as *provisional / AI-drafted***. Disagreement → held for Jaypaul tie-break.
- Provenance (authoring + validating models, sources) recorded on the item.
- **Assessment content is held to higher scrutiny** than practice content (it certifies readiness).

### Layer 2 — Runtime crowd validation (the human authority)

```
[Lesson/exercise] --"Provide feedback / corrections"-->
  Postgres feedback row (private: correction, optional email, consent)
    --> sanitized GitHub issue (feedback.id only, NO PII)
    --> SP6 agent: triage → evaluate → Codex-validate → trust-tiered:
          trusted contributor  → auto-merge PR
          new/anonymous        → human-gated PR
        → on outcome, email thank-you + result from noreply@nyolc.cc
    --> accepted crowd-verified corrections upgrade item to `community-verified`
```

- **Same MoE gate** guards crowd edits; submissions are sanitized (prompt-injection/harassment/spam), rate-limited, and **trust-tiered** before any auto-merge.
- Loop closure (every contributor hears back, by name, with an outcome) is the retention flywheel and costs nothing.
- **SP1 builds only capture** (private row + sanitized issue + rate limit + consent). Processing agent, trust/reputation system, email, and auto-merge are **SP6**.

### Infra introduced (SP6-time decisions)

- GitHub issue template + labels; **compliant transactional email** for `noreply@nyolc.cc` (provider choice + SPF/DKIM/DMARC + consent + unsubscribe/transactional classification + bounce/suppression); a **reputation/trust model** for tiering.

## 10. Risks & open questions

- **Accuracy without a native gate** — accepted trade-off (Jaypaul): provisional labeling + mandatory source citation + MoE + crowd. Residual risk of two LLMs sharing a wrong answer; mitigations = citations, prominent provisional badge, crowd weighting, assessment held to higher scrutiny, Jaypaul tie-break on holds.
- **Which accredited B2 exam** — provisionally **ECL** (chosen autonomously 2026-07-05: the most commonly accepted exam for Hungarian residency/citizenship purposes, four-skill format matching our engine, exam centres across Hungary). Confirm or override before B1/B2 assessment blueprints are authored (SP5 remainder).
- **HAL specifics** — confirm Docker + reverse-proxy/TLS + backup location before build.
- **Content-format + SRS-algorithm** finalization — decide at plan time (Drizzle already fixed).
- **Trust/reputation model** (SP6) is now load-bearing for auto-merge — design before enabling any auto-merge.
- **Free-forever vs AI cost** — hybrid, enforced SP2; free core stays genuinely free.
- **Scope discipline** — OAuth-only + tier-aware engine + versioning + GDPR is already a substantial MVP; resist pulling AI/audio/exams forward.
